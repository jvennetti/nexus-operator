## Brief

Everything in Claude Code until now was setup. Now you build.

"Build" sounds like it means software. It can, but mostly it means **making a thing that didn't exist, that does something useful, and that you can open tomorrow.** Some examples that non-technical operators build in their first week:

- A personal dashboard page that shows this week's priorities, pulled from a notes file.
- A tool that takes a folder of receipts and produces a clean expense spreadsheet.
- A page for a client with their project status, updated by editing one file.
- A simple form that turns answers into a formatted document.
- A script that renames and organizes a messy folder of downloads.

You describe it the same way you learned in Module 2: what it is, who it's for, what it needs to do, how it should feel. Claude Code builds it, shows you, and you give notes. The only new habit: **ask for it in steps.** "First, show me a plan. Then build the simplest version. Then we'll improve it." Big things built in one shot are hard to steer. Small steps are easy.

When something doesn't work, you don't need to understand why. Paste the error, or describe what you saw, and say "fix it." That sentence is most of what debugging is.

## Task

Build one useful thing for yourself.

1. **Choose something from your Operator List** that a small tool could help with, or pick one of the examples above. Smaller is better. You can make it bigger later.
2. **Ask for a plan first.** In your workspace: "I want to build [the thing]. It's for [who], and it needs to [what]. Before building anything, give me a short plan: what files you'll create and what the simplest working version looks like."
3. **Build the simplest version.** "Go ahead with the simplest version." Open the result. Use it for real, even if it's rough.
4. **Three rounds of notes.** What's wrong, what's missing, what should look different. Same discipline as Module 2.
5. **Break it and fix it.** Try something it wasn't built for. When it fails, paste the error or describe what happened and say "fix it." Notice that you didn't need to understand the problem.

Mark done when the thing exists and you've used it once.

## Takeaways

- Building means making something useful that didn't exist and that you can open tomorrow. It doesn't have to be "software."
- Ask for a plan, then the simplest version, then improve in rounds. Small steps are easy to steer.
- When it breaks, paste the error and say "fix it." You don't need to understand why.
