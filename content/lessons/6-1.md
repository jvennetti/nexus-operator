## Brief

This module is one project, broken into four lessons. You're going to pick one recurring piece of your work, and build the system that runs it. Not a demo. The real thing, on real data, that you keep using after the course ends.

The first lesson is choosing well. Three criteria:

- **It recurs.** Daily or weekly. A one-off isn't worth a system.
- **It's pattern work.** The same shape every time: information comes in, gets processed, goes somewhere. Reports, summaries, follow-ups, updates, intake, triage.
- **It costs you real time.** At least an hour a week. Go back to the note you made in Module 3 about what the morning routine saved. That's the kind of number you're looking for.

Then you map it. Every workflow, no matter how messy it feels, breaks down to four questions:

1. **Input.** What arrives, and where? Emails, a form, a folder of files, a task list, a calendar.
2. **Steps.** What has to happen to it? Read, extract, decide, draft, format, check.
3. **Output.** What comes out, in what shape? A document, a message, rows in a sheet, tasks in a tool.
4. **Destination.** Where does the output need to end up, and who sees it?

Once you've written those four answers down, you've designed the system. Everything else is assembly, using parts you already know: connectors for input and destination, a skill for the steps, a scheduled task to run it, Claude Code if it needs to touch files.

## Task

Pick and map the workflow you'll build.

1. **Shortlist from your Operator List.** Which items recur, are pattern work, and cost real time? Pick the one where all three are strongest. If torn, pick the one that annoys you most.
2. **Map it with Claude.** In your workspace:
```
I'm going to build a system that handles this workflow for me: [describe it in a few sentences]. Help me map it. Ask me questions until you can write a one-page WORKFLOW.md with four sections: Input (what arrives and where), Steps (what happens to it, in order), Output (what comes out and in what shape), and Destination (where it goes and who sees it). Then list which tools we'll need: which connectors, whether it needs a skill, whether it should be scheduled, and whether it needs Claude Code to handle files.
```
3. **Read WORKFLOW.md critically.** Is every step actually necessary? Is there a step you do by habit that could go? Edit it.
4. **Decide the first version.** The simplest version that would still be useful. Write a line at the bottom of the file: "Version 1 does: ..." Keep it small. You'll extend it in lesson 6.3.
5. **Save it** in your workspace. It's the spec for the next two lessons.

## Takeaways

- Pick something that recurs, is pattern work, and costs you at least an hour a week.
- Every workflow maps to four questions: input, steps, output, destination.
- Design the simplest useful version first. Extend it after it works.
